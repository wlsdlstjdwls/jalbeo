# 20. 검색어 로그 — 사이트 내 검색을 품목 후보 원천으로

2026-09-04. 사용자 요청: "검색어에 입력해서 조회한 걸로 저장해두고 그걸로
품목 추가해보는건 어때?"

## 배경

`docs/18` 13번은 씨앗을 사람이 아니라 발행분(품목명 + 별칭)에서 뽑는다고
정했다. 자동완성 재크롤이 그 축이다. 여기에 한 축을 더한다 — 실제로
사이트 검색창에 입력된 질의. 자동완성은 네이버 사용자 전체의 수요고,
사이트 검색 로그는 이미 잘버려에 온 사람이 "이 물건도 있나" 하고 찾다가
못 찾은 흔적이다. 신호의 성격이 다르다.

## 결정

1. **테이블은 `page_views`(0004)와 같은 원칙.** 개인정보 없음, RLS로 테이블
   직접 접근을 막고 `SECURITY DEFINER` 함수(`track_search_query`)로만 쓴다.
   저장하는 건 정규화한 검색어, 그 순간 화면에 몇 건이 걸렸는지(`hit_count`),
   방문자 무작위 UUID(`jalbeo_vid`, 페이지뷰 추적과 같은 값 재사용)뿐이다.
2. **`hit_count = 0`이 핵심 신호다.** 사이트에 있는 물건인데 검색이 못 찾은
   게 아니라(그건 검색 로직 버그), 사이트에 아예 없는 물건을 찾다가 실패한
   흔적이다. 부분 인덱스(`search_queries_miss_idx`)로 그 행만 빠르게 뽑는다.
3. **디바운스 800ms, 최소 2글자.** 매 키 입력마다 쏘면 "ㅅ", "소", "소파"
   세 줄이 남는다. 입력이 멈춘 뒤 한 번만, 그것도 자유 검색창 입력에서만
   보낸다(판정 칩 클릭, 무한스크롤은 검색어가 아니므로 안 잰다).
4. **읽기는 admin RPC를 안 만든다.** `/admin/`은 방문자 통계 화면이지 품목
   기획 화면이 아니다(`docs/17`). 이 데이터는 확장 작업(`scripts/`)이
   `scripts/admin_admins.py`와 같은 방식으로 DB 자격증명(`site/.env`)으로
   직접 조회한다. 트래픽이 쌓이기 전엔 조회 스크립트를 만들 이유도 없다.

## 구현

- `db/migrations/0007_search_queries.sql` — 테이블 + 함수. Supabase에 적용 완료.
- `site/src/pages/index.astro` — 검색 입력 리스너에 디바운스 로깅 추가.
  `apply()`가 계산한 `shown`을 `lastShown`에 저장해 뒀다가, 디바운스 타이머가
  울리면 그 값을 `hit_count`로 함께 보낸다. 키가 없으면(`SEARCH_ENDPOINT`가
  빈 문자열) 아무것도 안 쏜다 — `Base.astro`의 `trackable` 방어와 동일 패턴.
- 엔드투엔드 확인: curl로 RPC 직접 호출 -> `search_queries`에 적재 확인 ->
  테스트 행 삭제. `npm run build` 171페이지 정상.
