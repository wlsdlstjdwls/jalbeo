# 비판적 검토

> 원안: `01-original-plan.md` / 실측 근거: `03`, `04`, `05`

## 치명적 리스크 5개

### 1. 구글 스팸 정책 — 최대 위험

2024년 3월 코어 업데이트에서 **scaled content abuse** 정책 추가.
AI로 대량 생성한 템플릿 변주 페이지가 정확히 이 정책의 타겟이다.

3,000페이지 템플릿 사이트는 색인 자체가 안 되거나 수동 조치 대상이 된다.
"템플릿 티 안 나게 변주"로 피해가는 게 아니라, 페이지마다 **다른 곳에 없는 정보**가 있어야 통과한다.
수수료 표 하나 다르다고 고유 콘텐츠로 인정되지 않는다.

### 2. 경쟁 상대가 지자체 공식 사이트

"매트리스 버리는법 용산구" → 용산구청 공식 페이지가 상위.
정부기관 도메인 = 최상급 신뢰 신호. B층은 정면 승부로 못 이긴다.

원안은 B를 확장 축으로 잡았는데, 승산은 A에 있다. **우선순위가 반대로 설정돼 있었다.**

### 3. 네이버

한국에서 생활 검색어는 네이버 유입 비중이 크다.
네이버는 외부 웹사이트 색인에 인색하고 블로그·지식iN이 상위를 차지한다.
구글만 노리면 실제 파이의 절반 이하만 가져간다.

### 4. 데이터 유지보수 부담

수수료는 조례 개정마다 바뀐다. 100품목 × 30지자체 = 3,000 데이터포인트.
갱신 안 하면 틀린 정보 사이트가 된다 → 이탈률 상승 → 순위 하락.
크롤링 자동화 없으면 6개월 뒤 죽은 사이트가 된다.

### 5. 수익 기대치 과대

쓰레기 = 애드센스 CPC 최하위권 주제.
월 수십만 원 달성하려면 월 10만 PV 이상 필요. pSEO 사이트가 6개월 안에 도달할 규모가 아니다.

## 기술 스택 재검토

### 원안의 문제

Spring Boot + MariaDB + EC2 = 정적 콘텐츠에 서버 비용을 태우는 구조.
데이터는 자주 안 바뀌고, 로그인 없고, 개인화 없다. **DB와 애플리케이션 서버가 필요 없다.**

EC2 월 2~3만 원이 초기 수익을 전부 잡아먹는다.

### 변경안

| 항목 | 원안 | 변경 |
|---|---|---|
| 렌더링 | Spring Boot + Thymeleaf SSR | Astro 또는 Next.js **SSG** |
| 데이터 | MariaDB | JSON/CSV → 빌드타임 주입 |
| 호스팅 | EC2 | Cloudflare Pages / Vercel (무료) |
| 갱신 | 관리자 페이지 | 크롤러 → git commit → 자동 재빌드 |

SEO 효과는 SSR과 SSG가 동일하다. LCP는 SSG가 더 좋다. 비용은 0.

## 결론 — 구조 변경

1. **B층(품목 × 지자체 3,000페이지) 폐기**
2. **A층(품목 페이지 500~800개)에 전량 투자**
3. 지역 정보는 페이지를 곱하지 말고 **품목 페이지 내부 셀렉터/컴포넌트**로 처리
4. **"비용 / 무료수거 / 업체" 축 추가** — 검색 의도가 이미 거래 의도 (근거: `04`)
5. 지역 데이터는 공공데이터로 커버되는 경기권 먼저, 서울은 트래픽 확인 후 크롤링 투자 결정
